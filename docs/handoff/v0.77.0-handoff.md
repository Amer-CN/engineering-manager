## 2. 关键改动详情

### 累计待办 #1: cloud sync schema 准备

**最大改动, 4 文件 +591 行**:

#### migration 024_AddCloudSyncColumns.sql (233 行)

27 张业务表 × 5 列 + 27 个 `idx_<table>_version` 索引。

**列定义**:
- `version` INTEGER NOT NULL DEFAULT 1 — 乐观锁 CAS, INSERT 默认 1, UPDATE 时 `SET version = version + 1 WHERE id = @Id AND version = @OldVersion`, 0 行影响 = 冲突
- `last_modified_by_device` TEXT — 多设备追踪, 阶段 1 全 NULL, 阶段 2 设备注册后由后端注入
- `last_modified_at` TEXT — 冗余 `updated_at` 但专为 sync 设计 (`updated_at` = 用户面, `last_modified_at` = sync 面)
- `sync_status` TEXT NOT NULL DEFAULT 'synced' — 程序层约束 (`synced` / `pending` / `conflict`), 不加 SQLite CHECK 避免 ALTER ADD COLUMN 失败
- `conflict_marker` TEXT — 阶段 2 冲突检测用, 默认 NULL

**27 业务表** (按 user-dim P0-4 闭环清单):

## 4. 设计决策记录

### 范围收窄 (与设计文档差异)

| 设计文档说 | 本期实际做 | 理由 |
|---|---|---|
| 33 业务端点 INSERT/UPDATE 加 version 自增 | ❌ 留到 v0.78.0 阶段 2 | 范围太大 (80 SQL 修改), 阶段 1 先把 schema 落地, 阶段 2 sync 逻辑实施时一起改 endpoint |
| JWT refresh token | ❌ 留到 v0.78.0 阶段 2 | 设备注册 API 必须先有 (阶段 2), refresh token 才有用武之地 |
| sync worker 推/拉 | ❌ 留到 v0.78.0 阶段 2 | 阶段 1 决策: 不实现 sync 逻辑 |
| 冲突检测 UI | ❌ 留到 v0.78.0 阶段 2 | 阶段 2 才有冲突产生 |
| 5 列 + 2 新表 | ✅ 全部完成 | 这是阶段 1 的核心, 也是本 sprint 唯一交付 |

**理由**: 用户提示"阶段 1 (schema 准备 + 不动 sync 逻辑) 应该按 minor 算", 所以本 sprint 范围明确收窄到 schema. endpoint 改动需要配合 sync 逻辑一起做, 单独做版本号管理混乱.

### Schema 设计决策

1. **DEFAULT 1 / 'synced'**: 现有代码无需任何改动即可继续工作, INSERT 不指定这些列也能跑, 旧数据零成本迁移
2. **不加 SQLite CHECK 约束**: 老版本 SQLite 不支持 ALTER ADD COLUMN + CHECK, 程序层约束更灵活 (阶段 2 CloudSyncHelper 强制)
3. **只加 version 单列索引**: CAS 是高频查询 (`WHERE id=@Id AND version=@OldVersion`), sync_status / last_modified_at 索引在阶段 2 sync worker 实施后再加
4. **sync_queue 12 列**: 阶段 2 推/拉同步需要的全部字段 (含 attempt_count 失败重试, last_error 调试, payload JSON 行快照避免云端拉历史)
5. **device_registrations refresh_token_hash**: 明文 token 不存 db, 只存 SHA-256 哈希 (阶段 2 设备注册 API)

### 风险与缓解

| 风险 | 严重度 | 缓解 |
|---|---|---|
| 27 表 × 5 列 ALTER 在大库上慢 | 🟢 低 | ALTER ADD COLUMN 不锁表, SQLite 单文件微秒级 |
| DEFAULT 1 让所有现有行 version=1 | 🟢 低 | 预期行为, 阶段 2 sync 不会误判冲突 |
| sync_status='synced' 默认 | 🟢 低 | 阶段 2 sync worker 才会把 pending 行推完后改回 synced |
| 老版本 SQLite ALTER ADD COLUMN 失败 | 🟢 低 | 工程用 Microsoft.Data.Sqlite 10.0.8, 支持 ALTER ADD COLUMN |
| 33 业务端点不写 sync_queue | 🟢 低 | 阶段 1 决策: 端点暂不写, 阶段 2 sync 实施时一起改 |
